# The completion gate, run end to end: what the numbers were

Until this run the gate had never finished on this machine. Every earlier attempt
stopped inside step 4, and the standing record said so honestly: no semantic score
was claimed on any head. This note exists because a gate that cannot finish is not a
gate, and the honest label "not completed locally" was hiding a solvable problem.

## The cause was the wrapper, not the gate

Step 4 is the WCAG audit, and it runs the whole browser suite
(`vitest run --config vitest.e2e.config.ts`). That suite is deliberately serialised -
`fileParallelism: false`, a single fork - because the placeholder and dogfood suites
seed and sweep the same origin's cache, and running them concurrently has one suite
delete the cache out from under the other. Serial audio-visual verification against a
production build therefore takes minutes, and the tool shell that launched the gate
enforces a 295-second cap on a single command. The gate was being killed at the same
place every time.

Two earlier attempts made it worse rather than better: a backgrounded `nohup` run was
torn down with its shell (its log stops mid-step 4), and the only surviving evidence
was a `gate-report.json` from a run that never reached the judge.

## The cure

The gate is launched as a **persistent process** (`process_start`, a PTY that
outlives the command that started it) and polled. Nothing in the instrument moved:

- no step was split, skipped, re-scoped or parallelised;
- the browser suite still runs serialised, against the production build, with the
  Content-Security-Policy enforced;
- `REQUIREMENTS`, `JUDGE_ASPECTS`, the register and the 99 threshold are unchanged;
- the WCAG step is still a single command that must exit 0 to PASS.

The wall clock was never bounded by the gate; it was bounded by the caller. Fixing
the caller is the whole change, and it is a change to how the gate is invoked, not to
what it measures.

```
[1/4] typecheck + build ...                        PASS
[2/4] unit + security tests ...                    PASS

[4/4] WCAG 2.2 AA audit (axe-core, real browser)   PASS

Deterministic  101/101
Jev: jev-1.14.0 - 9621 in / 134 out
Overall: 79/100
```

`gate-report.json` at that head:

| Field | Value |
| --- | --- |
| `threshold` | 99 |
| `decision.checks` / `checksPassed` | 101 / 101 |
| `decision.deterministicOk` | true |
| `decision.semantic` | `measured` |
| `decision.score` | 79 |
| `decision.thresholdMet` | false |
| `decision.verdict` | `FAILED` |
| `decision.reason` | semantic score 79 against the 99 threshold |

This is the **semantic-only failure that is the settled state of this project**: the
deterministic layer is complete, the judge reads 79 against a frozen threshold of 99,
and the reason field names the semantic layer and nothing else. The instrument is
frozen at 99 and no product wording was changed to move this number.

## The same run again, at the commit that records it

The run above was made at `df2dca6`. Because a reading is only evidence if it belongs
to a head someone can check out, it was repeated at `bc039b9` - the commit that adds
this note and the repaired probe - with the same command, the same instrument and the
same process handling:

```
[1/4] typecheck + build                          PASS
[2/4] unit + security tests                      PASS
[3/4] live API contracts                         PASS
[4/4] WCAG 2.2 AA audit (axe-core, real browser)  PASS

Deterministic 101/101 | Overall 78.7/100 | verdict FAILED
  reason: semantic score 78.7 against the 99 threshold
  requirements_met (scored) = 0.895 (14/14 clauses)
  clause_7 noul=0.55, clause_11 noul=0.75, aspect_school_depth 0.52, aspect_ownership 0.53
```

Two runs of a stochastic judge are not the same number: 79 at `df2dca6`, 78.7 at
`bc039b9`, from the same deterministic result and the same evidence. That variance is
the honest shape of this instrument, and it is why the deterministic layer carries the
pass/fail load and the semantic layer is reported with its number rather than rounded
toward the threshold. The five lowest readings are the same five in both runs, and
`clause_7` - the clause whose text is frozen and reserved to the owner - is among them
every time.

Two properties of the reading are worth stating rather than leaving in a log:

- **The register caveat is still true.** The gate reports
  `independent_channel_ran: false` and `tree_complete` unmeant, because every clause
  question is menu-bound and no register-independent channel ran. A 79 here means
  "the supplied record is coherent to this degree", not "the tree is 79% complete".
- **The gate's own semantic layer has no control question.** That weakness is real,
  and it is why the lane runs `tools/probe-pass-e.mjs` separately: that probe carries
  a control whose answer is checkable by hand, and prints INVALID rather than a score
  when the control reads low. A gate reading without a control is evidence; a probe
  reading with one is evidence that the instrument works.

## What this closes

The claim "no semantic score is claimed on any head because the gate could not
finish" is retired: the gate finishes, and the score at these heads is 79 at
`df2dca6` and 78.7 at `bc039b9`, against 99, FAILED on the semantic layer only. `docs/jev-roadmap.md` carries the phase status,
and this note is the evidence for the row that says so.
